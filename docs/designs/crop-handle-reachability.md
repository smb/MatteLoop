# Design: Reachable crop handles

Generated by /office-hours on 2026-09-03, reviewed by /plan-eng-review the same day
Branch: chore/crop-handle-design
Repo: smb/MatteLoop
Status: REVIEWED (eng review + Codex outside voice, 2026-09-03)

## Problem Statement

The crop editor works, but its handles are hard to grab. Two independent causes,
both in the geometry layer:

**1. The frame is fitted flush to the widget border, so there is no room for a
handle.** `MediaTransform.scale` (`src/matteloop/core/geometry.py:311`) is
`min(viewport.width / display.width, viewport.height / display.height)`. On the
constrained axis the content rectangle touches the widget edge exactly. With the
default crop (the whole frame) the handle centres therefore land *on* that edge:
the 8x8 markers built at `geometry.py:586` are half-clipped, and
`_effective_target` (`geometry.py:928`) clamps the 24 px pointer region wholly
inward. Approaching the edge from outside hits the `PreviewStage` layout margin,
which is not a canvas at all.

**2. Only eight 24x24 boxes on the border are draggable; the rest of the border
moves the whole rectangle.** Each of the eight handles gets one square target. On
a 225 px tall left edge, 24 px drag the edge and roughly 200 px fall through to
the `"crop"` entry in `priority` (`geometry.py:613`) and translate the crop
instead. That is the "it slips away from me" half of the complaint.

Cause 1 is what was reported. Cause 2 is the larger share of the pain and costs
almost nothing to fix alongside it.

## What already exists

- `_TimelineTransform.inset` (`geometry.py:676`) — an inset field with a
  build-time clamp already exists on the sibling transform in this same file.
  `MediaTransform.inset` follows its shape rather than inventing one.
- `_effective_target(rect, viewport, minimum)` (`geometry.py:928`) already grows
  a rectangle to a minimum size and clamps it into the viewport. The edge bands
  reuse it; they must not be built directly (see Constraints).
- `PreviewCanvas.set_frame` (`preview_canvas.py:155`) already stores the QImage
  in `self._frame` and clears the placeholder text when an image arrives, so the
  paint-path change needs no new state for the image itself.
- `StatusLabel._load_status_icon` (`preview_canvas.py:95`) already demonstrates
  the `setDevicePixelRatio` pattern this repo uses for HiDPI assets.
- `_normalized_image` (`jobs/source.py:1084`) already returns the frame oriented
  and square-pixelled, so the decoded QImage dimensions equal
  `MediaTransform.oriented_display_size`. The image drops into `content_rect`
  with no further conversion. This is the precondition that makes the paint-path
  change viable.

## Constraints

- `core/geometry.py` is Qt-free and deterministic. The geometry belongs there,
  not in event handlers.
- **The edge bands must be produced through `_effective_target`.** Building them
  directly skips its viewport clamp and breaks
  `test_hit_targets_use_the_full_viewport_when_it_is_below_minimum_size`
  (`tests/core/test_geometry.py:153`), which asserts every target collapses to
  the whole viewport when the widget is smaller than one target.
- `core/geometry.py` is frozen at 1057 lines in `scripts/guardrails-baseline.json`.
  This change raises it; the new baseline must be reported to the maintainer.
- Verification: `uv run ruff check . && uv run mypy src &&
  QT_QPA_PLATFORM=offscreen uv run pytest -q`

## Premises

1. The reported symptom is the crop drag surface, not the file drop zone.
   Drag-and-drop lives in `ui/source_strip.py:95`; `CropCanvas` accepts no drops.
2. 16 px is a comfortable gutter, but reachability does not depend on it.
   Measured against `_effective_target` at viewport 100: a 16 px gutter leaves
   12 clickable pixels outside the image, an 8 px gutter leaves 8. The clamp
   keeps the whole gutter inside the band either way. An earlier draft asserted
   `_MEDIA_INSET >= _POINTER_TARGET / 2`; that relationship is not what carries
   the fix, and the runtime clamp in §3 violates it on small viewports while a
   constant-comparison test would stay green. Test reachability, not the ratio.

## Approaches Considered

Rejected during the office-hours session:

- **Edge bands only** — leaves the markers clipped and unreachable from outside.
- **Gutter only** — leaves the stretch between handles translating the crop.
- **Gutter + bands + handles offset outward (Figma style)** — deferred; the
  outward offset needs the focus-ring path reworked for a cosmetic gain.

Rejected during the engineering review:

- **Gutter in two places (Qt layout margins + `MediaTransform.inset`), as first
  drafted** — see Recommended Approach. It kept paint and geometry as parallel
  computations, which this repo has a standing decision against.

## Recommended Approach

### 1. One computation places both the image and the overlay

`CropCanvas` overrides `_update_pixmap` to a no-op and paints `self._frame`
itself into `geometry.transform.content_rect`. The layout margins stay 0 and the
gutter exists only as `MediaTransform.inset`.

```
        frame ──▶ MediaTransform ──▶ content_rect ──┬──▶ image
                        │                           ├──▶ crop rectangle
                        │                           └──▶ handles
                        └──▶ pointer / touch / focus / accessible rects
```

The first draft instead set the gutter twice — Qt's `KeepAspectRatio` scaling in
`preview_canvas.py:206` *and* `MediaTransform.inset` — and relied on the two
agreeing. They agree today only because both happen to compute the same fit.
`MediaTransform` already carries `zoom` and `pan` fields (`geometry.py:262`),
unused by `CropCanvas` so far; the moment zoom is wired up, Qt's scaling knows
nothing about it and the overlay detaches from the image. This repo has a
standing decision that paint, hit regions, focus and accessible rectangles come
from one `InteractionGeometry` snapshot for exactly that reason.

The placeholder path survives untouched: `set_frame(None)` restores the
placeholder text, and `set_frame(image)` clears it, so a `None` frame renders as
today.

**The image is painted before the crop guard.** `paintEvent` currently returns
early on `not self._active or self._geometry is None` (`crop_canvas.py:88`).
Today that is harmless because the base class already blitted the pixmap. Once
`CropCanvas` owns the image, drawing it after that guard would blank the source
whenever crop is switched off or the presentation is missing. Image first,
then the guard, then the overlay.

### 2. Scaling is cached; only positioning comes from the geometry

`paintEvent` runs on every mouse move during a crop drag. Scaling the source
image there would move a per-frame cost onto every pointer event. `CropCanvas`
keeps a scaled `QPixmap` plus the size it was built for, rebuilds it only when
that size changes, and blits it into `content_rect`. A crop drag does not change
`content_rect`, so it triggers no rescale; a zoom or resize does, and the cache
invalidates on its own because the size it keys on changed.

### 3. `MediaTransform.inset`, clamped where the sibling clamps

```python
inset = min(self.inset, self.viewport.width / 4, self.viewport.height / 4)
object.__setattr__(self, "inset", inset)
```

`inset` defaults to `0.0`, and only the crop display geometry passes a non-zero
value. This is not cosmetic: `crop.py:139` builds a `MediaTransform` as a
unit-scale orientation transform whose viewport equals the display size exactly.
A non-zero default would shrink that fit and corrupt every oriented-coordinate
conversion.

`scale` then fits into `viewport - 2 * inset` on both axes. The clamp is not
decorative: `crop_canvas.py:264` builds the viewport as
`SizeF(max(1, self.width()), max(1, self.height()))`, and those `max(1, ...)`
exist because Qt hands the widget through at zero width during layout. Without
the clamp, `SizeF` raises, `_rebuild_geometry` swallows it into
`self._geometry = None`, and the overlay silently disappears until the next
resize.

### 4. Full-length edge bands

In `build_crop_geometry`, the pointer and touch rectangles for `north`, `south`,
`east` and `west` span the whole crop edge instead of a square — west covers
`x ∈ [left - 12, left + 12]`, `y ∈ [top, bottom]`. They are produced through
`_effective_target`, per Constraints. The four corners keep their squares and
keep winning, because `priority` already lists them first. `visual` is untouched:
the markers stay 8x8; only what counts as a hit changes.

### 5. The four sizes get names and one asserted relationship

`_HANDLE_MARKER = 8.0`, `_POINTER_TARGET = 24.0`, `_TOUCH_TARGET = 44.0`,
`_MEDIA_INSET = 16.0` as module constants beside `_CROP_HANDLES`. The guard
against someone trimming the gutter is a reachability test over several gutter
values, not an inequality between two of the constants — see Premise 2.

### 6. Both previews render at device resolution

`_update_pixmap` scales to `size * devicePixelRatioF()` and calls
`setDevicePixelRatio`, the pattern `StatusLabel` already uses. The cover-frame
crop below it (`preview_canvas.py:219`) then has to compute in physical pixels
too, or it centre-crops against a logical size that no longer matches the
pixmap. Fixing it in the
shared path covers `result_canvas` too; the crop canvas gets device-resolution
rendering from its own paint path regardless, and without this the two previews
sit side by side at visibly different sharpness.

## NOT in scope

- **Handles offset outward from the crop edge (Figma style)** — cosmetic; needs
  the focus-ring path reworked.
- **Wiring up zoom and pan** — the fields exist and this change makes them safe
  to use, but nothing here exposes them.
- **A resize cursor or hover affordance on the edge bands** — full-length bands
  change what a click on the middle of an edge does, from translating the crop
  to resizing it, with no visible signal. Worth doing; not in this change.
- **A gutter on `result_canvas`** — it has no handles, so it needs no gutter.
- **Reworking the `PreviewCanvas` / `CropCanvas` inheritance** — the no-op
  `_update_pixmap` override is two lines; extracting a base class for one
  override would be premature.

| `paintEvent` | rescale per pointer event | GAP → add | size-keyed cache (§2) | yes, as stutter |
| `build_crop_geometry` | band escapes the viewport | `test_geometry.py:153` | `_effective_target` | would be silent |

No critical gap remains: every silent failure above is closed by a clamp or a
guard, and each is paired with a test below.

## Test plan

Three existing tests break and must be rewritten, not deleted:

- **CRITICAL — `tests/ui/test_crop_canvas.py:129`** compares `content_rect`
  against `canvas.pixmap().width()`. After §1 there is no pixmap and `pixmap()`
  returns `None`. This is the most valuable test in the suite: it is the only one
  proving paint and geometry agree. Rewrite it to assert `content_rect` matches
  where the frame is actually painted.
- **CRITICAL — `tests/ui/test_crop_canvas.py:146`** pins `transform.scale` to
  `478 / 1280`. The inset changes the scale and therefore the expected crop after
  an 80 px drag.
- **CRITICAL — `tests/ui/test_controller.py:83`** asserts
  `window.original_canvas.pixmap()` is non-null. After §1 the crop canvas never
  sets a pixmap. Assert the frame reached the canvas instead.

The core geometry tests are NOT affected: `test_geometry.py:66`, `:111`, `:167`
and `test_crop.py:58` build their `CropGeometryState` without an inset, and the
field defaults to `0.0`.

New tests:

1. `test_geometry.py` — `content_rect` is inset on both axes; `inset` is clamped
   at a 1x1 viewport and the geometry still builds.
2. `test_geometry.py` — a point 8 px outside the frame hit-tests to the adjacent
   handle.
3. `test_geometry.py` — a point a quarter of the way down the left edge
   hit-tests to `west`, not `crop`.
4. `test_geometry.py` — parametrised over several gutter values: a point just
   outside the content rectangle hit-tests to the adjacent edge handle. This
   replaces the constant-ratio assertion an earlier draft proposed.
5. `test_crop_canvas.py` — a drag started outside the frame emits `CropChanged`.
6. `test_crop_canvas.py` — `set_frame(None)` still shows the placeholder.
7. `test_crop_canvas.py` — repeated paints at an unchanged `content_rect` scale
   the source once, but a new frame of identical dimensions is displayed rather
   than served from the cache.
9. `test_crop_canvas.py` — the source frame is still painted when crop is
   inactive and when the presentation is absent.
10. `test_geometry.py` — a `MediaTransform` built without an explicit inset is
    unchanged from today, so `crop.py`'s orientation transform is unaffected.
8. `test_preview_canvas` — the pixmap's device pixel ratio matches the widget's.

## Implementation order

1. `core/geometry.py`: named constants (§5), `MediaTransform.inset` with the
   clamp (§3), inset-aware `scale` and `content_rect`, plumbed through
   `CropGeometryState`.
2. `core/geometry.py`: full-length bands through `_effective_target` (§4).
3. `ui/preview_canvas.py`: device pixel ratio in `_update_pixmap` (§6).
4. `ui/crop_canvas.py`: no-op `_update_pixmap`, cached scaled pixmap, paint into
   `content_rect` (§1, §2).
5. Rewrite the two breaking tests, add the eight new ones.
6. Raise the guardrail baseline. `core/geometry.py` is frozen at 1057 lines and
   this adds roughly 30-40. The maintainer agreed to the growth during this
   review, which is the order `docs/engineering-guardrails.md:288` requires;
   run `uv run python scripts/check_guardrails.py --update` as part of the
   implementation and name the reason and the new figure in the commit body.

Steps 1-2 and step 3 touch different files and can run in parallel; step 4
depends on both, and step 5 on step 4.
