# Design: Reachable crop handles

Generated by /office-hours on 2026-09-03
Branch: fix/swscale-destination-overrun
Repo: smb/MatteLoop
Status: DRAFT
Mode: Builder

## Problem Statement

The crop editor works, but its handles are hard to grab. Two independent causes,
both in the geometry layer:

**1. The frame is fitted flush to the widget border, so there is no room for a
handle.** `MediaTransform.scale` (`src/matteloop/core/geometry.py:311`) is
`min(viewport.width / display.width, viewport.height / display.height)`. On the
constrained axis the content rectangle touches the widget edge exactly. With the
default crop (the whole frame) the handle centres therefore land *on* that edge:
the 8x8 markers built at `geometry.py:586` are half-clipped, and
`_effective_target` (`geometry.py:928`) clamps the 24 px pointer region wholly
inward. Approaching the edge from outside hits the `PreviewStage` layout margin,
which is not a canvas at all.

**2. Only eight 24x24 boxes on the border are draggable; the rest of the border
moves the whole rectangle.** Each of the eight handles gets one square target. On
a 225 px tall left edge, 24 px drag the edge and roughly 200 px fall through to
the `"crop"` entry in `priority` (`geometry.py:613`) and translate the crop
instead. That is the "it slips away from me" half of the complaint.

Cause 1 is what was reported. Cause 2 is the larger share of the pain and costs
almost nothing to fix alongside it.

## Constraints

- `core/geometry.py` is Qt-free and fully deterministic. The fix belongs there,
  not in event handlers.
- Painting and hit-testing must stay derived from a single transform.
  `PreviewCanvas._update_pixmap` (`ui/preview_canvas.py:200`) scales the pixmap
  through `self.layout().contentsMargins()`; `CropCanvas.__init__` currently
  zeroes those margins. Any inset must be applied in both places or the overlay
  desynchronises from the image.
- `docs/engineering-guardrails.md` freezes several modules against growth.
  `core/geometry.py` and `ui/crop_canvas.py` need checking against
  `scripts/guardrails-baseline.json` before the diff lands.

## Premises

1. The reported symptom is the crop drag surface, not the file drop zone.
   Drag-and-drop lives in `ui/source_strip.py:95`; `CropCanvas` accepts no drops.
2. A gutter is a display change: the original preview renders slightly smaller.
   Acceptable — `result_canvas` already uses `set_cover_frame(True)` against the
   original's `False`, so the two panes are not scale-matched today either.
3. 16 px is enough gutter. The pointer target is 24 px (+/-12) and the touch
   target 44 px (+/-22); 16 px gives the pointer target full room on both sides
   of the edge and most of the touch target.

## Approaches Considered

Rejected during the session:

- **Edge bands only** — one file, ~10 lines, but leaves the markers clipped at
  the widget border and still unreachable from outside.
- **Gutter only** — makes the eight handles reachable but leaves the stretch
  between them translating the whole crop.
- **Gutter + bands + handles offset outward (Figma style)** — the fuller
  version; deferred because it also needs the focus-ring path reworked
  (`focus=visual` in `build_crop_geometry`) for a purely cosmetic gain.

## Recommended Approach: gutter plus full-length edge bands

Chosen because it removes both causes in one pass, in the layer that owns them,
for roughly 25 lines.

**Gutter.** Add `inset: float = 0.0` to `MediaTransform`. `scale` fits into
`viewport.width - 2 * inset` by `viewport.height - 2 * inset` (guard the result
against a non-positive box when the widget is smaller than the inset — fall back
to the uninset fit rather than raising, per the degrade-never-refuse rule).
`content_rect` stays centred in the full viewport, so every widget coordinate
remains widget-absolute and no caller needs a translation.

Thread it through `CropGeometryState` so `build_crop_geometry` passes it on.
In `CropCanvas.__init__`, replace `setContentsMargins(0, 0, 0, 0)` with the same
value and pass it as `inset`. That single number then drives both paths: Qt
shrinks the pixmap through the layout margins and centres it in `contentsRect()`,
which lands in exactly the rectangle `MediaTransform.content_rect` predicts.

**Edge bands.** In `build_crop_geometry`, the pointer and touch rectangles for
`north`, `south`, `east` and `west` span the full crop edge instead of a square:
west becomes `x` in `[left - 12, left + 12]`, `y` in `[top, bottom]`, and so on.
The four corners keep their squares and keep winning, because `priority` already
lists them first. `visual` is untouched — the markers stay 8x8, only what counts
as a hit changes.

## Open Questions

- Should the gutter also apply to `result_canvas` so the two panes line up? It
  has no handles, so it needs no gutter; leaving it is the smaller diff.
- Corner-versus-band precedence at short edges: when a crop edge is under about
  24 px long the corner squares cover it entirely and the band is unreachable.
  Harmless (the corners do the same job there), but worth one test.

## Success Criteria

- With the default full-frame crop, every handle marker is fully painted and a
  click 8 px outside the frame grabs the nearest edge.
- A click anywhere along an edge, not just at its midpoint, drags that edge.
- A click in the interior still translates the crop.
- `uv run ruff check . && uv run mypy src && QT_QPA_PLATFORM=offscreen uv run pytest -q`
